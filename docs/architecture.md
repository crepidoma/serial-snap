# アーキテクチャ

## 構成

```
写真 ─ 画面（src/client）
        │ createImageBitmap → canvas で画素にする（長い辺4000px・検出用に1920px）
        ▼
      Web Worker（src/ocr/worker.ts）
        │ core.ts  文字の検出（DBNet）→ 傾きを直して切り出し → 文字の認識（CTC）
        │ qr.ts    QRコードを読む（zxing-wasm）
        │ parse.ts シリアルとURL・QRコードを見分け、シリアルごとに応募先（アーティスト）を付ける
        ▼
      画面 ─ 読み取り1回分として IndexedDB に保存し、応募先ごと・10件ずつに表示
```

| 場所 | 役割 |
| --- | --- |
| `src/client` | React の画面。 |
| `src/ocr` | 読み取りのWorker。`core.ts`・`parse.ts` はNode.jsからも動かす（`scripts/eval-ocr.ts`）。 |
| `src/shared` | 画面とWorkerとブックマークレットで使う型と判定。 |
| `src/bookmarklet` | ブックマークレットの元のコード。ビルド時に圧縮して画面に渡す。 |
| `src/assets` | PaddleOCR（PP-OCRv4）の検出・認識モデルと文字の一覧。 |

## 読み取り

PaddleOCR の PP-OCRv4 を onnxruntime-web（WASM）で動かす。OpenCV を使わず、必要な幾何計算（凸包・最小外接長方形・回転した切り出し）を `core.ts` に書いている。OpenCV.js は数MB増えるため。

- **向き**: 検出した行は長い辺を読む向きにし、まず読む。確信度が0.9未満なら180°回して読み直し、高い方を使う。逆さまの行は確信度がほぼ0になるため見分けられる。
- **速さ**: 説明文の細かい行まで読むと時間の大半をそこに使う。行の高さが中央値の1.2倍以上の行（シリアル・URLなど）だけを先に読み、シリアルが1件も見つからなかったときだけ残りも読む。
- **シリアル**: 英大文字と数字だけの10〜20文字で、英字と数字を両方含む行。
- **英字だけのシリアル**: 一緒に写った説明書などの英単語と見分けるため、次のどちらかに当てはまる行だけを拾う。
  - 紙の上でシリアルがある位置にある（右隣にQRコード、またはすぐ上に応募サイトのURL）
  - 同じ写真のほかのシリアルと、文字数が同じで文字の高さもほぼ同じ（±25%）
  - 数字だけの行は拾わない。伝票の番号はQRコードの横に並ぶことがあり、誤認しやすいため。
- **応募先**: 紙に印刷された `ticket.fortunemeets.app/<アーティスト>/` と、QRコード（中身は同じURL。ドメインは fortunemusic.app のこともある）から、アーティスト部分を取り出す。次の順に決める。
  1. シリアルの右隣・同じ高さにあるQRコード（紙の作りで、QRコードはシリアルの枠のすぐ右にある）
  2. シリアルの上、行の高さの5倍以内にあるURL（末尾の「/」まで読めたもの）。試した写真では同じ紙のURLは2.3〜3.4倍、上に重ねた別の紙のURLは7.8倍以上離れていた
  3. 写真の中の応募先が1種類なら、それ
  4. どれもなければ「応募先不明」
- **縦にずらして重ねた紙**: シリアルを見やすく並べるとURLは上の紙に隠れ、QRコードだけが見える。QRコードを先に使い、URLを探す範囲を狭くしているのはこのため。
- **URLの読み違い**: 「nogi-aka46」のような1〜2文字の読み違いは、似ている度合い（レーベンシュタイン距離）で同じアーティストとみなし、読み取り1回の中で多数決をとる。

### 試した結果（2026年10月）

実物の紙の写真11枚（1枚・45°傾き・逆さま・4枚・4枚バラバラ・10枚でシングル3種類が混在・4枚を縦にずらして重ねたもの・3枚を横に重ねたもの・その暗い写真・白い背景・関係のない紙が混ざったもの）で、写っているシリアル35件をすべて正しく読み、応募先も正しく付けた。関係のない紙の文字をシリアルと誤認しなかった。処理時間は紙10枚の写真でNode.jsが約3秒。QRコードの読み取りを足す前の計測では、Chromium（WASM・1スレッド）が約11秒、WebKitが約15秒だった。

## 保存

- 読み取り1回ごとに、日時・シリアル・応募先・確信度・コピー済みの印・切り抜き（JPEG）を IndexedDB に保存する。切り抜きはlocalStorageに入りきらないため。
- 起動のたびに30日を過ぎたスキャンを消す。
- 写真そのものは保存しない。シリアルナンバーが見つからなかった写真だけ、まとめの画面で示すための小さな見本（長い辺240px）を、次のスキャンを始めるまでメモリに置く（端末には保存しない）。
- テーマの設定、ブックマークレットの案内を出したかどうかは localStorage に置く。

## クリップボード

- 10件ずつのコピーでは、`text/plain`（1行に1件）と `text/html`（目印・応募先・何件目から何件目か）を同時に書く。独自の形式（`web application/…`）はiPhoneのSafariが対応していないため、`text/html` に目印を入れる。
- ブックマークレットは「クリップボードから入力」を押したときだけクリップボードを読み、`text/html` に目印があるときだけ入力する。目印がなければ理由を出し、手で貼り付ける入力欄を使ってもらう。関係のない内容（パスワードなど）を応募サイトの入力欄に入れないため。読み取りはボタンを押した直後に始める（Safariは利用者の操作の直後でないと読ませない）。
- 目印は `text/html` の本文の1行（`シリアルスナップ（nogizaka46 1-10/14）`、`src/shared/marker.ts`）。ブラウザはHTMLを読み出すときに属性や `meta` を削ることがあるため、文字として入れる。終わりを閉じ括弧で示すのは、本文を取り出すと次の行（数字で始まるシリアルナンバー）とつながるため。
- iPhoneのSafariは別のサイトでコピーしたHTMLを読むときに一部を削ることがあるため、目印が残るかは実機で確かめる。

## ブックマークレット

- `src/bookmarklet` を `scripts/vite-bookmarklet.ts` がビルドのときに1つのファイルへまとめて縮め、`virtual:bookmarklet` で `javascript:` のURLとして画面に渡す。
- パネルは Shadow DOM の中に作り、応募サイトのCSSの影響を受けないようにする。Panda CSS は使えないため、色の値は `panda.config.ts` と同じものを書く。
- 応募サイトの登録画面（2026年10月に確かめた）: 入力欄は `id="inputSerial1"` から始まり、初めは3つ、「＋ 入力枠を追加」で10個まで増える（10個で押すボタンが消える）。`maxLength` はその企画のシリアルナンバーの文字数。入力欄とボタンは1つのフォームの中にあり、ボタンはどれも `type="submit"` だが、「入力枠を追加」を押してもフォームは送信されない。画面は React で作られており、本来の setter で値を入れて `input` イベントを送ると状態に反映される。
- アプリの画面（`index.html` の `meta[name="serial-snap"]`）で開くと「追加完了」を出し、`serial-snap:bookmarklet` イベントで知らせる。アプリはそれを受けて追加済みと記録する。

## 画面の骨組み

- 画面全体の高さを `100dvh` にし、ヘッダーを上、操作の帯を下端に固定して、その間だけをスクロールさせる。ホーム画面に追加して開くと、上部がスクロールする領域だとiPhoneでは端末の時計などの部分にぼかしがかかるため。
- ノッチとホームバーの分の余白を `env(safe-area-inset-*)` で取る（`viewport-fit=cover`）。

## 配布物とキャッシュ

- `vite build` で静的ファイルを出力する。`base: "./"` で相対パスにし、GitHub Pagesのようにパスの途中に置かれても動かす。
- 初回に約31MB（WASM 14MB・認識モデル 11MB・検出モデル 5MB・QRコードのWASM 1MB）を取得する。画面を開くとWorkerが取得を始め、進み具合を出す。
- `scripts/vite-sw.ts` がビルドのときに、全ファイルの一覧と版の名前を `src/sw/sw.ts` に埋め込み、`sw.js` を出力する。版の名前は、ファイルの名前（`assets/` はハッシュ入り）と、`index.html`・`public/` のファイルの中身から作る。開発サーバーでは登録しない。
- 画面（`index.html`）は通信を優先し、つながらなければ保存したものを返す。ほかのファイルは保存したものを優先する。
- 新しい版は、入れ替えのときにモデルとWASM以外を保存し、すぐに制御を引き継ぐ（`skipWaiting`）。モデルとWASMは画面が取得するときに保存する（取得の進み具合を画面に出すため。保存を待たずに画面へ返す）。前の版で保存した `assets/` のファイルは、名前が同じなら引き継ぎ、もう一度ダウンロードさせない。
- モデルの取得は、Service Workerがページを制御し始めてから行う（`src/client/lib/sw.ts`。最大10秒待つ）。先に取得すると、その通信が保存されないため。
- ホーム画面に追加したとき（案内はしない）の名前とアイコンは `public/manifest.webmanifest` に書く。アイコンのPNGは `npm run icons`（`scripts/make-icons.ts`）で `public/icon.svg` から作る。iPhone と Android の切り抜き用（maskable）は、端末が角を丸めるため、角を丸めずに地を端まで敷く。

## 制約と判断

- **複数スレッドはヘッダーがあるときだけ**: 文字認識の複数スレッドには、ページを分離する COOP/COEP のヘッダーが要る。Cloudflare Pages では `public/_headers` で付け、ないとき（GitHub Pagesなど）は1スレッドで動かす。紙10枚などの写真4枚で、Chromiumは25.9秒→12.6秒、WebKitは31.3秒→16.0秒になった。onnxruntime-web の1ファイルにまとめた版は、スレッドを作るときに自分を含むファイル（このWorker）を読み込んで止まるため、`env.wasm.wasmPaths.mjs` に付属のファイルを指定する。
- **写真のデコードは画面側**: Workerで画像を扱う `OffscreenCanvas` が使えないブラウザがあるため。iPhoneのSafariはcanvasの画素数に上限（約1,670万）があり、長い辺を4000pxに縮める。
- **React 19 と `javascript:` URL**: React 19 は `href` に `javascript:` を渡すと無効にするため、ブックマークレットのリンクは ref でDOMに直接設定する。
- **zxing-wasm のWASM**: 既定では外部（jsDelivr）から読み込むため、このサイトから取得して `wasmBinary` で渡す。
- **CSP**: `index.html` の meta で `connect-src 'self'` などを指定する。WASMの実行に `'wasm-unsafe-eval'` が要る。
- **書体**: シリアルは IBM Plex Mono（Fontsource の Latin の版、太さ500・600、1つ約15KB）をこのサイトから配る。自分で文字を絞り込むと改変になり、SIL OFL の予約名の決まりにかかるため、配布されている版をそのまま使う。外部のフォントは読み込まない。
